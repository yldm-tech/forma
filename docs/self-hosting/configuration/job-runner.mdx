Forma runs asynchronous work, such as the response pipeline, webhooks, integrations, survey scheduling and [Workflows](/workflows/overview), as background jobs. The jobs are queued in PostgreSQL with [River](https://riverqueue.com) and worked by `forma worker`, a process of the same `forma` binary and image as the server. Valkey (`REDIS_URL`) no longer holds a job queue; it keeps rate-limit counters and short-lived state only.

<Note>
  Upgrading from forma2? Its BullMQ queue in Redis is not carried over: jobs still queued in Redis when forma2 stops are not run by the Go server. Let the forma2 instance drain its queue before the switch. `BULLMQ_WORKER_CONCURRENCY` and `BULLMQ_WORKER_COUNT` still work and are read as `WORKER_CONCURRENCY` (see below); `BULLMQ_EXTERNAL_WORKER_ENABLED` is ignored. See the [upgrade guide](/self-hosting/advanced/migration#forma2-to-the-go-server).
</Note>

## Where the worker runs

| Deployment | Worker |
| --- | --- |
| Docker Compose and the one-click install | The `forma-worker` service runs `forma worker`, next to the `forma` service running `forma serve`. |
| Helm | The `worker` Deployment (`worker.enabled`, on by default) runs `forma worker`; the server pods get `BULLMQ_WORKER_ENABLED=0`. With `worker.enabled=false` the server pods run the jobs in-process. |
| The image's default command, `forma start` | Serves and works jobs in the same process, as forma2's web container did, unless `BULLMQ_WORKER_ENABLED=0`. |

`forma serve` only enqueues jobs, and `forma worker` only works them. Every process that enqueues or works jobs connects to the same PostgreSQL database (`DATABASE_URL`), so there is nothing else to share between replicas. Jobs are enqueued in the same database transaction as the change that causes them: a response that is saved always has its pipeline job, and a rolled-back change never leaves a job behind.

`forma migrate` creates River's tables (`river_job`, `river_queue`, `river_leader`, ...) after the schema migrations, so the migration job (the `forma-migrate` service, the Helm migration Job, or the start of `forma start`) must have run before a worker starts.

## Configure the worker

| Variable | Description | Default |
| --- | --- | --- |
| `WORKER_CONCURRENCY` | How many jobs one worker process runs at once. `0` derives it from the CPU count: `max(2, min(4, logical CPUs))`, forma2's default. Each running job can hold a database connection, so keep it below `DATABASE_MAX_OPEN_CONNS`. | `0` |
| `BULLMQ_WORKER_CONCURRENCY`, `BULLMQ_WORKER_COUNT` | forma2's settings. When `WORKER_CONCURRENCY` is unset and either is set, the worker runs `BULLMQ_WORKER_COUNT x BULLMQ_WORKER_CONCURRENCY` jobs at once (a missing one takes forma2's default: one worker, `max(2, min(4, logical CPUs))` jobs) and logs a deprecation warning at start-up. When `WORKER_CONCURRENCY` is set they are ignored, with a warning. | unset |
| `BULLMQ_WORKER_ENABLED` | Read by `forma start` only: `0` serves without the in-process worker, for deployments that run `forma worker` separately. | `1` |
| `SHUTDOWN_TIMEOUT` | On SIGTERM the worker stops taking jobs and gives the running ones this long to finish before cancelling them. | `20s` |
| `DATABASE_MAX_OPEN_CONNS` | The connection pool of one process. | `20` |
| `SURVEY_SCHEDULING_TIME_ZONE`, `SURVEY_SCHEDULING_LOCAL_HOUR`, `SURVEY_SCHEDULING_LOCAL_MINUTE` | When the daily survey scheduling and archive sweeps run. | `Europe/Berlin`, `0`, `0` |

Restart the worker after changing a value. To work more jobs, raise `WORKER_CONCURRENCY` or run more workers: `docker compose up -d --scale forma-worker=2`, or `worker.replicas` in Helm. Total capacity is the sum of the concurrency of every worker process; River coordinates them through PostgreSQL, and periodic jobs are scheduled by one elected worker only.

## Background jobs

| Workload | Job kinds | Schedule |
| --- | --- | --- |
| Response pipeline | `response-pipeline.process` | On every response event; it hands off to webhooks, integrations, follow-up emails and workflows. |
| Response files | `response.delete-files` | When responses with uploaded files are deleted. |
| Survey scheduling | `survey-scheduling.reconcile` | Daily at `SURVEY_SCHEDULING_LOCAL_HOUR:SURVEY_SCHEDULING_LOCAL_MINUTE` in `SURVEY_SCHEDULING_TIME_ZONE`. |
| Survey archive | `survey-archive-purge.process` | Daily. |
| Workflows | `workflow-run.process`, `workflow-run.reconcile`, `workflows-usage.snapshot` | Runs on demand, reconciliation every three minutes, the usage snapshot daily at 02:45 UTC. |
| Authorization | `authzed-projection.deliver`, `authzed-reconciliation.audit` | Delivers the SpiceDB projection outbox every five seconds; audits the projection every six hours. |
| Retention | `retention-sweep.process`, `auth.cleanup-expired`, `oauth.cleanup-expired` | The retention sweep daily; expired sessions, verifications and OAuth tokens hourly. |
| Billing (Forma Cloud) | `billing.setup-organization`, `billing.cleanup-customer` | On organization changes. |
| Usage report | `usage-telemetry.process` | Daily at 02:15 UTC and when the worker starts; it sends only with `TELEMETRY_ENABLED=1`. |
| Smoke test | `system.test-log` | Never on its own; when one is enqueued, the worker logs its message at debug level. |

A failed attempt is retried after 5 s, 10 s, 20 s, ...; a job gets three attempts. Completed jobs are kept for 24 hours and discarded ones for 7 days, then River deletes them.

## Workflows

Workflows run on the same worker; there is no other process to deploy. Configure the services the actions you use need, for example SMTP for **Send email** (see [SMTP Configuration](/self-hosting/configuration/smtp)).

<Warning>
  Workflow delivery retries and recovers; it is not exactly-once. Runs and steps move through guarded transitions so that a redispatch is safe, but expect a job to run again after a transient failure.
</Warning>

A periodic reconciliation recovers workflow runs that lost their job: queued runs that waited too long are redispatched, very old queued runs are marked failed, and running runs without executor activity are failed with their unfinished steps skipped. When it changes runs it logs `Workflow run reconciliation acted` with the `queued` and `stuck_running` counts.

## Verify and troubleshoot

The processes write one JSON object per line to stdout (see [Monitoring](/self-hosting/setup/monitoring)). Search the `msg` field:

| Log message | Meaning |
| --- | --- |
| `job queue migration applied` / `job queue schema is up to date` | `forma migrate` applied River's migrations, or found nothing to do. |
| `job worker started` | `forma worker` (or `forma start`) is working jobs. River logs `River client started` with its `client_id` just before. |
| `starting the server and the job worker` / `starting the server without the job worker (BULLMQ_WORKER_ENABLED=0)` | What `forma start` runs. |
| `BULLMQ_WORKER_CONCURRENCY and BULLMQ_WORKER_COUNT are deprecated; set WORKER_CONCURRENCY=<n> instead` | forma2's settings are in use; set the value it names. |
| A River line whose `msg` ends in `Job errored; retrying` or `Job errored` | A job attempt failed. `job_kind`, `job_id` and `error` say which and why; after the third attempt the job is discarded. |
| `job worker shutting down` | SIGTERM; running jobs get `SHUTDOWN_TIMEOUT` to finish. |

If jobs do not run:

1. Check that a worker is running: `docker compose ps forma-worker`, or the `worker` Deployment in Kubernetes, and that its log has `job worker started` after the last restart.
2. Check that the migrations ran (`job queue schema is up to date` in the migration's log): the worker needs River's tables.
3. Look at the queue itself in PostgreSQL: `SELECT kind, state, count(*) FROM river_job GROUP BY 1, 2;` shows what is waiting (`available`, `scheduled`, `retryable`) and what failed (`discarded`, with the errors in `river_job.errors`).
4. With Prometheus or OTLP metrics on, `forma_jobs_wait_duration_seconds` (how long jobs waited past their due time) is the backlog signal, and `forma_jobs_processed_total` counts settled jobs by `job_name` and `status` (`completed` or `failed`).

See [Environment Variables](/self-hosting/configuration/environment-variables) for every setting.
