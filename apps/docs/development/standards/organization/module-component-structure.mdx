## Introduction

The admin UI (`apps/web/src/`) has two primary organizational units, and the Go server mirrors the first:

1. **Feature modules**: domain-specific screens, logic and API calls, one directory per feature in `apps/web/src/features/` (and one package per feature in `apps/server/internal/`)
2. **UI components**: reusable building blocks in `apps/web/src/components/` (the generic ones in `apps/web/src/components/ui/`)

## Module Organization

### Core Module Structure

A feature module typically includes:

```
apps/web/src/features/
└── feature-name/
   ├── components/    # the feature's own components
   ├── lib/           # business logic and utilities, with their tests
   ├── api.ts         # the feature's calls through `api` (apps/web/src/lib/api.ts)
   ├── api.test.ts
   └── types.ts       # types the feature does not share
```

The route that shows a feature lives in `apps/web/src/routes/` and stays thin: it declares the path, prefetches the page's queries in its loader and renders a page component from the feature. Query factories shared by several features live in `apps/web/src/lib/queries/`.

On the server, the matching unit is a package, `apps/server/internal/<feature>/`, layered handler → service → repository; see [File and Directory Organization](/development/standards/organization/file-and-directory-organization).

## Component Organization

### UI Component Structure

Generic components live in `apps/web/src/components/ui/`, one file per component, or a directory when a component has parts of its own:

```
apps/web/src/components/ui/
├── button.tsx
├── dialog.tsx
├── dialog.test.ts
└── file-input/
   ├── index.tsx      # the component
   ├── components/    # its sub-components
   └── lib/           # its logic
```

The survey runtime's components are in `packages/survey-ui`, with their Storybook stories (`apps/storybook`).

### Component Types

1. **Base Components**: fundamental UI elements like Button, Input, Dialog, in `apps/web/src/components/ui/`

2. **Composite Components**: components that combine base components, such as the data table or the date picker

3. **Feature-Specific Components**: components tied to one feature, in that feature's `components/`

### Feature Module Example

```
apps/web/src/features/surveys/
├── ai-create/
├── list/
├── templates/
├── api.ts
├── api.test.ts
├── defaults.ts
└── defaults.test.ts
```

## Best Practices

1. **Component Organization**
   - Keep components focused and single-purpose
   - Type props explicitly
   - Meet basic accessibility: labelled controls, keyboard operation, visible focus

2. **Module Structure**
   - Organize by feature domain
   - Separate business logic (testable without rendering) from UI components
   - Keep server data in TanStack Query, not in component state

3. **Code Sharing**
   - Share generic components through `apps/web/src/components/ui/` and helpers through `apps/web/src/lib/`
   - A feature does not reach into another feature's internals; move what both need to `components/` or `lib/`
   - Import with relative paths; shared packages by their `@forma/*` names
