## forma2 to the Go server

Forma now runs as a Go server instead of forma2's Next.js application. Its image has a new name, `ghcr.io/yldm-tech/forma-server`, with versions `0.2.<n>`; `ghcr.io/yldm-tech/forma`, the image forma2's compose file, one-click installer and Helm chart pull, keeps forma2's last release. Pulling again leaves an installation on forma2; it moves to the Go server by taking the new compose file or chart, as the steps below describe. forma2's compose file cannot run the new image: it starts its containers with `sh`, `node` and `forma-authzed` entrypoints the new image does not have.

### What changes

- **One distroless image, several processes.** The image holds a single binary, `/usr/local/bin/forma`, on a distroless base running as uid 1001, with no shell, no Node.js and no `forma-authzed`. Its subcommands are the processes: `forma serve` (HTTP on `:3000`), `forma worker` (background jobs), `forma migrate` (schema, then the job queue's tables), `forma start` (the default command: forma2's entrypoint, validating the configuration, migrating unless `SKIP_STARTUP_MIGRATION=true`, then serving with the worker in the same process unless `BULLMQ_WORKER_ENABLED=0`), `forma authz` (SpiceDB operations), `forma wait-for-database`, `forma healthcheck` and `forma version`. Replace `docker exec ... sh -c '...'` and `kubectl exec ... -- node ...` with `forma <command>` or the `postgres` container.
- **A separate job worker.** The Compose stack runs `forma worker` as the `forma-worker` service and the chart as the `worker` Deployment. See [Job Runner](/self-hosting/configuration/job-runner).
- **River on PostgreSQL instead of BullMQ on Redis.** Background jobs are queued in PostgreSQL in the transaction of the change that causes them. Valkey keeps rate-limit counters, caches and locks only; jobs still queued in Redis when forma2 stops (webhook and integration deliveries, follow-up emails, workflow runs) are not run by the Go server, so switch in a quiet window.
- **Sessions live in PostgreSQL** and forma2's sessions are not carried over: everyone signs in again once.
- **`forma authz` instead of `forma-authzed`**, with the same `schema`, `backfill` and `outbox` commands; `health` and `upgrade prepare|check` map to them as listed in [AuthZed Operations](/self-hosting/advanced/authzed-operations#move-from-forma2s-authzed-tooling).
- **Configuration** keeps forma2's variable names, with these differences (`./forma.sh update` handles each of them):
  - `DATABASE_URL` and `MIGRATE_DATABASE_URL` may keep Prisma's `?schema=public`, which is dropped; any other `schema` value fails the start. Remove it when you edit the URL anyway.
  - The Prisma connection parameters of those URLs need no change either: `pgbouncer`, `connection_limit`, `pool_timeout`, `max_connection_lifetime`, `max_idle_connection_lifetime`, `socket_timeout`, `statement_cache_size` and `query_timeout` are dropped (size the pool with `DATABASE_MAX_OPEN_CONNS`), `statement_timeout` and `idle_in_transaction_session_timeout` keep forma2's seconds for the server and worker and are not applied to migrations, and `sslaccept` or `sslidentity` fail the start: say them with `sslmode`, `sslrootcert`, `sslcert` and `sslkey`.
  - `BULLMQ_WORKER_CONCURRENCY` x `BULLMQ_WORKER_COUNT` becomes `WORKER_CONCURRENCY` (they are still honoured, with a deprecation warning, while `WORKER_CONCURRENCY` is unset).
  - `CRON_SECRET`, `AUTHZED_SYSTEM_KEY`, `ENTERPRISE_LICENSE_KEY`, `OIDC_SIGNING_ALGORITHM`, `AUTH_SKIP_INVITE_FOR_SSO`, `AUTH_SSO_DEFAULT_TEAM_ID`, `BULLMQ_EXTERNAL_WORKER_ENABLED`, `DEBUG` and the other [ignored variables](/self-hosting/configuration/environment-variables#variables-forma2-read-that-the-go-server-ignores) are not read.
  - A missing required variable or a malformed value stops the process at start-up instead of being ignored. Switches are `1` or `0` (`AUTHZED_ENABLED` and `AUTHZED_INSECURE` also take `true`/`false`).
  - Keep `ENCRYPTION_KEY` (it opens the two-factor secrets) and `NEXTAUTH_SECRET` / `BETTER_AUTH_SECRET` (they verify the link survey tokens forma2 sent) exactly as they are.
- **Logs** keep the lowercase `level` labels, `audit` included, but `time` is an RFC 3339 string and `pid`, `hostname` and `name` are gone; `LOG_LEVEL` defaults to `info` where forma2 defaulted to `warn`. See [Monitoring](/self-hosting/setup/monitoring) and [Audit Logging](/self-hosting/advanced/enterprise-features/audit-logging).
- **Static assets** are under `/assets/*` (fingerprinted) instead of `/_next/static/*`; adjust CDN rules as described in [CDN](/self-hosting/configuration/cdn).
- **No custom subpath**: `BASE_PATH` has no counterpart; see [Custom Subpath](/self-hosting/configuration/custom-subpath).
- **PostgreSQL 18 or newer** is required. forma2's compose file already ran PostgreSQL 18; its Helm chart ran 17 (see the chart's [PostgreSQL upgrade](https://github.com/yldm-tech/forma/blob/main/deploy/helm/forma/README.md#upgrading-the-bundled-postgresql-from-17-to-18)).

### The database

The Go server keeps its data in tables of its own (`users`, `surveys`, ...), next to forma2's tables (`"User"`, `"Survey"`, ...) in the same database: `forma migrate` creates them without touching forma2's, and `forma import-forma2` copies forma2's data into them (see [Import forma2's data](#import-forma2s-data)). Started on a database where only forma2's tables hold data, the Go server would serve an empty instance whose first sign-up becomes its owner, so it refuses to start (`forma start`, `serve` and `worker` all check) while forma2's `User` table has rows and no import has been recorded. It also refuses when forma2's tables changed after the latest import, as they do when forma2 runs again after a [roll back](#roll-back): started then, it would serve without what forma2 wrote since. `./forma.sh update` runs the same checks before it starts the new stack.

Before anything else, back up the database (both `forma` and SpiceDB's `spicedb`), `.env` and your compose file or Helm values, and note the image your forma2 containers run, by digest, so you can return to exactly that release.

```bash
umask 077
docker compose exec -T postgres pg_dump -U postgres -d forma > forma2-forma.sql
docker compose exec -T postgres pg_dump -U postgres -d spicedb > forma2-spicedb.sql
docker image inspect --format '{{index .RepoDigests 0}}' "$(docker inspect --format '{{.Image}}' "$(docker compose ps -q forma)")"   # the forma2 image, by digest
```

### Import forma2's data

`forma import-forma2` copies forma2's data into the Go server's tables. It reads forma2's tables in one read-only snapshot and writes the Go server's tables in one transaction, so a run imports everything or nothing, and it never writes forma2's tables: forma2 can be started on them again as they were.

Run it after `forma migrate` and after stopping forma2, since anything forma2 writes after the copy is not imported. It connects through `MIGRATE_DATABASE_URL` when that is set, else `DATABASE_URL`; behind PgBouncer, give it the direct connection, as `forma migrate` needs. It needs `ENCRYPTION_KEY` and `NEXTAUTH_SECRET` (and `BETTER_AUTH_SECRET`, if forma2 had one) exactly as forma2 ran with them: they open forma2's two-factor secrets and integration credentials, which it encrypts again for the Go server.

```bash
forma import-forma2 --dry-run   # import, verify and print the counts, then roll everything back
forma import-forma2             # import, verify and commit
```

- **Ids.** Every forma2 id becomes a UUID derived from it, so survey links, SDK snippets, API calls and webhook receivers that still carry an old id reach the same survey, workspace or response.
- **Verification.** Before it commits, the import checks what it wrote against forma2's tables read again, apart from the queries that copied them: every forma2 row is there under the id derived from its own key, and in a sample of up to 20 rows of each table every column holds what the check computes on its own from forma2's stored columns (timestamps read as UTC, ids derived again, two-factor secrets and integration credentials opened and compared with what forma2's decrypt to). Every survey document must also pass the editor's validation (a draft needs only the shape a draft save needs; what a draft still lacks is listed as a warning) and every segment filter must be one the Go server can evaluate. When anything fails, the run lists it, writes nothing and exits 1. Warnings (a survey with two default languages, a workflow run forma2 had not finished, a credential that does not decrypt with `ENCRYPTION_KEY`) are printed and the run goes on.
- **The record.** The last write of a run is a row in `forma2_imports`, the record the startup check waits for. It keeps a digest of the Go server's tables as the import left them, and the row counts and newest update times of forma2's tables as the import read them.
- **SpiceDB.** The import queues the authorization projection of every imported organization, membership, team, workspace and API key, which `forma worker` delivers. With `AUTHZED_ENABLED=1` and SpiceDB reachable, the import also runs `forma authz backfill --apply` itself; otherwise run it once SpiceDB is up. Give the Go server a SpiceDB datastore of its own rather than forma2's (see [AuthZed Operations](/self-hosting/advanced/authzed-operations)): the two never delete each other's relationships automatically, but a prune from either side would, and both audits would report the other's relationships as drift.
- **Again.** A second run is refused unless you pass `--refresh`, which makes the imported tables what forma2 holds now: changed rows are updated and rows forma2 no longer holds are deleted. It refuses when the Go server has changed those tables since the record, since it cannot tell those changes from forma2's: it would bring back rows deleted through the Go server (a revoked API key, a removed member), delete rows created through it and overwrite what was changed. `--refresh --overwrite-changes` does exactly that, on purpose, when forma2's rows are the ones to keep (see [Roll back](#roll-back)).
- **Elsewhere.** `--source=<postgres url>` reads forma2 from another database than the one the Go server uses.
- **Starting empty.** To start the Go server on such a database without forma2's data, on purpose, run `forma import-forma2 --discard-forma2-data --reason="<why>"`, which records that decision instead. After a roll back, the same command records that the Go server keeps its own data and leaves what forma2 wrote after the import behind.

What is not carried over, and what users notice:

- Sessions: everyone signs in again once. Passwords, two-factor authentication and single sign-on identities are carried over.
- Password reset and email verification links sent before the switch: request a new one.
- Pending invitations: their links were tokens the Go server does not read, so resend them from the organization settings.
- MCP and other OAuth clients: they register and authorize again on their own.
- Jobs still queued in forma2's Redis (webhook and integration deliveries, follow-up emails), and workflow runs forma2 had not finished, which are imported as canceled.

### One-click installations

Download the current installer, replacing forma2's `forma.sh`, and run the update from the directory that contains `forma/`:

```bash
curl -fsSL https://raw.githubusercontent.com/yldm-tech/forma/stable/deploy/docker/forma.sh -o forma.sh
chmod +x forma.sh
./forma.sh update
```

It recognises forma2's compose file and, before touching the running stack:

1. keeps `docker-compose.yml.forma2-<timestamp>` and `.env.<timestamp>`;
2. moves the settings forma2's installer wrote into the compose file (`WEBAPP_URL`, `NEXTAUTH_URL`, `NEXTAUTH_SECRET`, `ENCRYPTION_KEY`, SMTP, the S3 settings, the auth switches) into `.env`, and its Traefik service and labels into `docker-compose.override.yml`;
3. updates `.env` as listed above, and maps the bundled RustFS credentials (`FORMA_RUSTFS_*`) to the compose file's storage profile (`COMPOSE_PROFILES=storage`, `RUSTFS_ADMIN_*`, `S3_*`);
4. writes the release's `docker-compose.yml`, `authzed-postgres-bootstrap.sh` and `rustfs-init.sh`, and checks the result with `docker compose config`.

Then it pulls the images, checks the database as described above, and runs `docker compose up -d`: `forma-migrate` runs `forma migrate`, `authzed-initialize` runs `forma authz schema apply`, and `forma` and `forma-worker` start. On a forma2 installation the first run stops at the database check, before anything is started, and prints the commands that import the data:

```bash
docker compose stop forma                                   # forma2's server
docker compose run --rm forma-migrate                       # the Go server's schema, next to forma2's tables
docker compose run --rm forma-migrate import-forma2 --dry-run
docker compose run --rm forma-migrate import-forma2
./forma.sh update
```

Every step is idempotent. After the stack is up, `docker compose --profile authzed-ops run --rm authzed-ops backfill --apply` rebuilds SpiceDB's relationships from the imported data.

### Docker Compose installations

`forma.sh update` works on any Compose directory: run `FORMA_DIR=. ./forma.sh update` inside it. To do the same by hand:

1. Download the release's files next to the old ones:

   ```bash
   for file in docker-compose.yml authzed-postgres-bootstrap.sh rustfs-init.sh; do
     curl -fsSL -o "$file.new" "https://raw.githubusercontent.com/yldm-tech/forma/stable/deploy/docker/$file"
   done
   ```

2. Move every setting your old `docker-compose.yml` sets under `environment:` for the `forma` service (forma2's file kept `WEBAPP_URL`, `NEXTAUTH_URL`, `NEXTAUTH_SECRET`, `ENCRYPTION_KEY` and the commented SMTP and S3 blocks there) into `.env`. The new file reads everything from `.env` and sets only `DATABASE_URL`, `REDIS_URL`, `TRUSTED_PROXY_HOP_COUNT` and the SpiceDB connection itself.
3. Edit `.env`: remove `?schema=public` from any database URL, replace `BULLMQ_WORKER_CONCURRENCY`/`BULLMQ_WORKER_COUNT` with `WORKER_CONCURRENCY`, and remove the ignored variables. Keep `POSTGRES_PASSWORD`, `POSTGRES_PASSWORD_URL_ENCODED`, `AUTHZED_TOKEN` and `AUTHZED_DATABASE_PASSWORD`.
4. Move your own additions (a reverse proxy, labels, extra volumes) into `docker-compose.override.yml`, which Docker Compose merges on its own, so later updates can replace `docker-compose.yml` without losing them. If you used forma2's `minio`/`rustfs` services for uploads, the new file has RustFS under the `storage` profile; see [Docker Setup](/self-hosting/setup/docker#enable-rustfs-for-file-storage).
5. Replace the files and check the result: `mv docker-compose.yml.new docker-compose.yml` (and the two scripts, `chmod 700` them), then `docker compose config >/dev/null`.
6. Pull the images, stop forma2 (`docker compose pull && docker compose stop forma`), apply the schema and import the data (`docker compose run --rm forma-migrate`, then `docker compose run --rm forma-migrate import-forma2`, see [Import forma2's data](#import-forma2s-data)), then `docker compose up -d --remove-orphans`.

### Helm installations

The chart in this repository (`deploy/helm/forma`) replaces forma2's and keeps its values, Secrets and resource names; its [README](https://github.com/yldm-tech/forma/blob/main/deploy/helm/forma/README.md#forma-on-the-go-server-what-changed-in-this-chart) lists the differences. In short:

- Set `deployment.image.tag` to the release you deploy, and remove `deployment.image.repository` from your values if it names forma2's `ghcr.io/yldm-tech/forma` (the chart's default is `ghcr.io/yldm-tech/forma-server`). The server runs `forma start` with `BULLMQ_WORKER_ENABLED=0`, and the new `worker` Deployment runs `forma worker` (`worker.enabled=false` returns to one Deployment).
- The migration Job runs `forma wait-for-database` and `forma migrate`; the AuthZed initialization Job runs `forma authz` steps instead of `forma-authzed upgrade prepare`. An upgrade still needs `authzed.migrationAcknowledged=true` once `forma authz schema apply`, `outbox drain` and `backfill --apply` have succeeded.
- Remove `enterprise.enabled`, `enterprise.licenseKey` and `authzed.systemKey`; the generated Secret no longer has `CRON_SECRET` or `ENTERPRISE_LICENSE_KEY`.
- The bundled PostgreSQL is 18; a release whose bundled database still runs forma2's 17 is refused until its data has been moved, as the README describes.
- With the chart's Envoy gateway in front, add `GATEWAY_RATE_LIMITING: "1"` to `deployment.env` so the server does not limit the covered routes a second time.
- Import forma2's data once the migration Job has run, from a one-off pod with the release's image and the server's Secret: `forma import-forma2` with `MIGRATE_DATABASE_URL` set to a direct (not pooled) connection. The server pods refuse to start until it has run, and start on their next restart after it.

```bash
helm upgrade forma ./deploy/helm/forma -n forma -f values.yaml --set deployment.image.tag=0.2.<n>
```

### Verify

1. `docker compose ps -a` (or `kubectl get pods`): `forma-migrate` and `authzed-initialize` exited with code 0, `forma` and `forma-worker` are running.
2. `curl -fsS https://<your domain>/health` answers, and `/health/ready` answers 200.
3. Sign in, open a survey and its responses, and submit a test response through a link survey; the worker's log shows the pipeline job.
4. `docker compose --profile authzed-ops run --rm authzed-ops schema check` and `outbox status` exit 0.

### Roll back

Stop the new stack, restore `docker-compose.yml.forma2-<timestamp>` and `.env.<timestamp>` (or your previous Helm values), set the forma2 image to the digest you noted (`image: ghcr.io/yldm-tech/forma@sha256:...`), and start it again. Neither `forma migrate` nor `forma import-forma2` modifies forma2's tables, so forma2 starts on them as they were; anything written through the Go server since the switch is not in them. The Go server's tables stay next to forma2's.

Once forma2 has run again, the Go server refuses to start on those tables (and `./forma.sh update` stops) until you decide what happens to what forma2 wrote in between. Stop forma2 first, then:

- If the Go server never changed its tables (it was stopped before anyone used it), `forma import-forma2 --refresh` imports forma2's tables as they are now.
- Otherwise the two sides have diverged and cannot be merged, and `--refresh` refuses. Either keep forma2's data, the usual choice after users went back to forma2: `forma import-forma2 --refresh --overwrite-changes` makes the Go server's tables forma2's, deleting what was created through the Go server, bringing back what was deleted through it (revoked API keys, removed members) and overwriting what was changed. Or keep the Go server's data: `forma import-forma2 --discard-forma2-data --reason="<why>"` records that what forma2 wrote after the import is left behind.

## v6

Forma v6 replaces the legacy authorization evaluator with AuthZed SpiceDB. PostgreSQL remains the source
of roles and grants, but SpiceDB is the sole decision engine. There is no runtime fallback, so an existing
installation must migrate through the bridge-compatible v5 release identified in the v6 release notes.

Before selecting a v6 image:

1. Back up the Forma and SpiceDB PostgreSQL databases, secrets, deployment configuration, image versions,
   and canonical schema digest.
2. Merge the release-matched AuthZed deployment services or Helm values without overwriting proxy, storage,
   SMTP, or external-datastore customization.
3. Run the v6 database migrations while the bridge application remains available.
4. Run `forma-authzed upgrade prepare`, then require `forma-authzed upgrade check` to exit `0`.
5. For one-click or Compose, set `FORMA_AUTHZED_V6_MIGRATION_ACKNOWLEDGED=true`. For Helm, set
   `authzed.migrationAcknowledged=true` in the v6 upgrade values.
6. Deploy v6 and verify critical allow, deny, revocation, and cross-tenant cases.

The update scripts and chart fail before replacing the running release when the deployment contract,
acknowledgement, schema, outbox, or relationship graph is not ready. Do not bypass the acknowledgement to silence
a failed gate. See [AuthZed Operations](/self-hosting/advanced/authzed-operations#move-from-forma2s-authzed-tooling)
for Docker and Kubernetes commands, guarded schema replacement, backups, repair, and rollback.

The moving `latest` image tag remains on the bridge-compatible v5 release for at least 30 days after v6 stable
publication. Existing installations opt into v6 explicitly during that migration window.

### Changes in Environment Variables

<Note>
  Both variables below drive SSO just-in-time provisioning, which is part of the Forma
  [Enterprise Edition](/self-hosting/advanced/license). On a community instance they have no effect, so
  there is nothing to rename.
</Note>

- **DEFAULT_ORGANIZATION_ID** has been renamed to **AUTH_SSO_DEFAULT_ORGANIZATION_ID**, matching the
  `AUTH_SSO_DEFAULT_TEAM_ID` naming pattern. Rename the variable in your configuration; the value is
  unchanged. Support for this variable was missing between v3.0 and v5.x, so it takes effect again on v6.

- **DEFAULT_ORGANIZATION_ROLE** has been renamed to **AUTH_SSO_DEFAULT_ORGANIZATION_ROLE**.

## v5.4

v5.4 adds no new environment variables. It does ship
**seven database migrations**, applied automatically during the upgrade. Six are quick — new columns and
tables, two of them data migrations that run on their own. The seventh builds an index on the `Response`
table, and it is the one that needs scheduling: it blocks response writes while it builds. Other
migrations add indexes too, but only on new or small tables. See
[Database migrations](#database-migrations) before scheduling the upgrade.

v5.4 also upgrades the **Better Auth** authentication core to 1.7. That upgrade needs no manual database
step — every migration is additive and applies automatically, including the backfills over existing rows —
and **your SSO callback URLs do not change**. It carries one narrow exception, and only for custom code: an
MCP access token is now bound to the session that authorized it, so an integration that caches one across
sessions has to fetch a fresh token — see
[MCP access tokens now end with their session](#mcp-access-tokens-now-end-with-their-session).

The bundled Valkey image moves from an amd64-only 8.1.1 image to the native amd64/arm64 Valkey 8.1.9 Alpine
image. Fresh Docker and Helm installations receive it automatically. Existing installations that retain an
older Compose file or explicitly reuse the previous Helm digest need the one-time update below.

### Database migrations

All seven migrations apply automatically during the upgrade. Two want something from you first: one needs
`WEBAPP_URL` set if you use MCP OAuth, and one deserves a scheduling decision on large instances. So here
is the full list rather than a summary:

| Migration | What it does | Impact |
| --- | --- | --- |
| `add_organization_display_time_zone` | Adds the nullable `Organization.displayTimeZone`, which formats response timestamps in file exports and in the payloads pushed to Google Sheets, Slack and Airtable (Notion is passed a raw date and is unaffected). | Instant |
| `eng_2343_better_auth_17_resource_model` | The Better Auth 1.7 schema: the `oauthResource` tables, resource columns on OAuth tokens and consents, `alg`/`crv` on `jwks`, and `Account.issuer` with its backfill. Details in the Better Auth 1.7 section below. | Additive and fast. The issuer backfill is what keeps password sign-in working on 1.7, so it must not be skipped — it runs on its own, listed here so it is not mistaken for optional |
| `eng_2343_backfill_oauth_resource_links` | Data migration linking existing MCP OAuth clients, refresh tokens and consents to this instance's `${WEBAPP_URL}/api/mcp` resource, so already-registered MCP clients survive the upgrade. It is a no-op only when the instance has no OAuth client at all, which in practice means a fresh install. | **Set `WEBAPP_URL` before upgrading if you use MCP OAuth.** The resource identifier is derived from it, so on an instance that has OAuth clients an unset or unparseable `WEBAPP_URL` fails this migration and stops the upgrade — set it and re-run |
| `add_response_survey_finished_index` | Adds an index on `Response(surveyId, finished)` so the survey list's response counts are served from the index instead of scanning the table. | **Blocks response writes while it builds — see the warning below** |
| `repair_account_issuer` | Data migration rewriting `Account.issuer` rows that were written with a non-canonical value, which locked the affected Google SSO users into a sign-in loop. Idempotent; a no-op when nothing is wrong. | Fast |

<Warning>
  `add_response_survey_finished_index` builds its index with a plain `CREATE INDEX`, not `CREATE INDEX
  CONCURRENTLY` — migrations run inside a transaction, and Postgres does not allow concurrent builds
  there. The build holds a `SHARE` lock on `Response`: reads keep working, but **survey responses cannot
  be written until the index is built**. `Response` is usually the largest table on an instance. On small
  instances the build takes seconds; if yours holds millions of responses, run the upgrade in a window
  where a short pause in response collection is acceptable.

  Neither documented deployment avoids this, so plan the window either way. On Kubernetes the chart runs
  migrations in their own job while the pods already running keep serving traffic, so the responses
  arriving during the build are the ones that block. On Docker Compose the app container does **not** wait
  for `forma-migrate` — it has no `depends_on` on that service and skips startup migrations itself —
  so after the documented `docker compose down && docker compose up -d` the two come up in parallel: you
  get downtime while the app boots, and then blocked writes for however much of the index build is left
  once it starts serving.
</Warning>

None of the seven constrains a rollback. v5.3 reads none of the new columns and tables, and the two
`NOT NULL` columns added to existing tables both carry a database default, so a v5.3 instance keeps
writing to those tables exactly as before. Rolling the application images / Helm values back to v5.3 is
safe without touching the database.

Coming back **forward** has one catch, and only if accounts were created while you were rolled back.
`Account.issuer` does not exist in v5.3, so any account signed up or linked on that version is written
without one — and both issuer backfills are already recorded as applied, so rolling forward does not
re-run them. Better Auth 1.7 keys accounts on `(issuer, accountId)`, which makes those rows invisible to
password sign-in and password reset. SSO accounts repair themselves on the next successful sign-in;
password accounts have no such path. If anyone signed up during the rollback window, re-run the repair
after rolling forward. This is the statement the `repair_account_issuer` migration runs, and it is
idempotent — it matches the providers v5.4 ships, so if you have since enabled one that is not listed
here, take the current mapping from that migration rather than this copy:

```sql
UPDATE "Account"
SET "issuer" = CASE
  WHEN "provider" = 'credential' THEN 'local:credential'
  WHEN "provider" = 'google' THEN 'https://accounts.google.com'
  ELSE 'local:oauth:' || "provider"
END
WHERE "issuer" IS DISTINCT FROM (
  CASE
    WHEN "provider" = 'credential' THEN 'local:credential'
    WHEN "provider" = 'google' THEN 'https://accounts.google.com'
    ELSE 'local:oauth:' || "provider"
  END
);
```

### Bundled Valkey 8.1.9 Upgrade (action required for some self-hosted deployments)

The old bundled digest selects only `linux/amd64`. The new digest selects the matching native image on
`linux/amd64` and `linux/arm64`, without requiring QEMU or `binfmt`. Valkey 8.1.9 also contains upstream
security fixes that are not present in 8.1.1.

<Warning>
  Valkey stores sessions, queues, cache entries and rate-limit state in the named `redis` volume with AOF
  enabled. Do not run `docker compose down -v`, delete the volume, or use `FLUSHDB` during this upgrade.
  Recreating only the container preserves the volume. Expect a brief interruption while Valkey restarts.
</Warning>

### Better Auth 1.7 upgrade (no action required for most instances)

v5.4 upgrades the Better Auth authentication core from the 1.6 line to 1.7, which fixes
[GHSA-p2fr-6hmx-4528](https://github.com/advisories/GHSA-p2fr-6hmx-4528): MCP OAuth access-token audiences
are now bound to the resource a user actually approved during authorization, instead of trusting whatever
the client requested. This is a coupled core upgrade — it touches login, sessions, 2FA, SSO and MCP OAuth —
but for self-hosted instances it needs no manual database step. Every schema change is additive and nullable,
and the required backfills (account identity, existing OAuth clients, refresh tokens, consents) run
automatically during the upgrade — they are the two `eng_2343` entries in the
[Database migrations](#database-migrations) table above.

The migration also adds two nullable columns, `alg` and `crv`, to the `jwks` table that holds your
instance's JWT signing keys. Keys created before the upgrade keep working untouched — Better Auth reads a
null `alg` as the default algorithm — so there is nothing to backfill, but the columns must exist before
the new version mints its next key.

#### AZUREAD_TENANT_ID: set a concrete tenant for full id_token verification

Better Auth 1.7 verifies Microsoft id_tokens against the issuer advertised by the tenant's OpenID
discovery document whenever `AZUREAD_TENANT_ID` names a concrete tenant — a Directory (tenant) ID GUID or
a verified domain. That is strictly stronger than v5.3 and needs no action.

Two of Microsoft's multi-tenant authorities are different. `common` and `organizations` advertise the
literal placeholder `https://login.microsoftonline.com/{tenantid}/v2.0` as their issuer, so verifying
real tokens against it fails every Microsoft sign-in with `?error=unable_to_get_user_info`. Forma
therefore handles those two the way it already handles an unset `AZUREAD_TENANT_ID`: sign-in identity
comes from Microsoft's userinfo endpoint over a client-authenticated call (the v5.3 behavior) and
id_tokens are not verified. The authority you configure still applies at sign-in, so `organizations`
keeps restricting sign-in to work/school accounts, and an unset value behaves as `common`. Forma
logs a warning at startup when either is set and Microsoft SSO is enabled. To get full id_token
verification, set your Directory (tenant) ID instead.

`consumers` needs no action and is not affected: every personal Microsoft account lives in one
well-known tenant, so that authority advertises a real issuer and keeps full id_token verification.

#### SSO callback URLs are unchanged

Your SSO callback URLs stay exactly as they are:

| Provider | Callback URL | Action required? |
| --- | --- | --- |
| Azure AD / Entra ID | `https://your-domain.com/api/auth/oauth2/callback/azuread` | No |
| Generic OIDC / Keycloak | `https://your-domain.com/api/auth/oauth2/callback/openid` | No |
| SAML (BoxyHQ / Jackson) | `https://your-domain.com/api/auth/oauth2/callback/saml` | No |
| Google / GitHub | `https://your-domain.com/api/auth/callback/{provider}` | No |

Better Auth 1.7 rebuilds its generic-OAuth support on top of the built-in social-provider route, which
would otherwise have moved these three callbacks to `/api/auth/callback/{providerId}` and required you to
register a new redirect URI at your identity provider. OAuth requires redirect URIs to match exactly, so a
path change means editing every provider configuration by hand.

Forma pins the callback URL instead, so it no longer follows the authentication library's internal
routing. The URLs above are the ones introduced in v5.2 and they are now a stable part of the Forma
API — a future authentication-core upgrade will not move them either.

<Note>
  The table writes `your-domain.com` as your `WEBAPP_URL`, which is correct for a default install. If you
  set `BETTER_AUTH_URL` or `NEXTAUTH_URL` to a different origin, the callback lives on **that** origin
  instead — it is derived from the same auth base URL Better Auth itself uses, not from `WEBAPP_URL`.
  Either way it is unchanged by this upgrade.
</Note>

<Note>
  Nothing to do, and nothing to undo. If you added a `/api/auth/callback/{providerId}` redirect URI in
  advance based on an earlier draft of these notes, leaving it registered is harmless — most identity
  providers accept several redirect URIs, and Forma simply will not use it.
</Note>

#### MCP access tokens now end with their session

An MCP access token used to stay valid until its own expiry, independently of the session that authorized
it. In 1.7 it is bound to that session: once the session ends — the user signs out, or the session is
revoked — the token is inactive. `/introspect` reports `active: false` for it and
`/api/auth/oauth2/userinfo` rejects it, rather than honouring it until its TTL runs out.

This is upstream hardening, and it is the stricter of the two behaviours: a token that outlives the sign-out
which created it is exactly what a revocation is supposed to stop.

It applies to **access** tokens. A refresh token granted `offline_access` deliberately survives the session
ending, per OIDC Back-Channel Logout 1.0 §2.7, so that long-lived API access can outlive a browser session —
which is what MCP clients rely on. Signing out is therefore not a way to cut a client off permanently.

**No action is required.** MCP clients re-authorize on their own — Claude Code and MCP Inspector both do —
so a user who signs out and back in sees nothing. It is listed here for one case only: a custom integration
that caches a Forma MCP access token and reuses it across sessions will start receiving rejections
where it previously succeeded, and should obtain a fresh token instead of treating the cached one as valid
until its expiry.

#### Rollback (Better Auth 1.7)

The `Account.issuer` column and the new `oauthResource`, `oauthClientResource` and `oauthClientAssertion`
tables are additive and nullable, and are not read by v5.3, so rolling the application images / Helm values
back to v5.3 is safe without touching the database. SSO needs no attention in either direction: v5.3 and
v5.4 use the same callback URLs. If accounts are created while you are rolled back, see the

## v5.3

Forma v5.3 is a **drop-in upgrade for most self-hosted instances**. There are no breaking API,
webhook, or authentication changes, and every database migration is additive and runs automatically on
startup. The only self-hosting-relevant changes are a few new optional variables. The main thing worth
setting before you deploy is `TRUSTED_PROXY_HOP_COUNT` for your proxy setup; everything else is optional.

<Info>
  All new environment variables are optional and defaulted — none of them block startup. You can upgrade
  to v5.3 without changing any environment variables and everything will run.
</Info>

### Client IP Resolution Behind a Proxy (recommended)

v5.3 resolves the client IP from the `X-Forwarded-For` chain using a configurable number of trusted proxy
hops:

- `TRUSTED_PROXY_HOP_COUNT` — optional, **defaults to `1`**. Set it to the number of trusted proxies /
  load balancers in front of Forma (e.g. an ingress plus a CDN = `2`). An explicit `0` trusts no
  proxy at all: the runtime exposes no socket peer address, so the client IP then resolves to a fixed
  "untrusted" placeholder that rate limiting and response audit logging record in place of a real address.
  A forwarding chain shorter than the configured count, or a malformed selected hop, also fails closed.
  Ports appended by gateways such as
  [Azure Application Gateway](https://learn.microsoft.com/en-us/azure/application-gateway/how-application-gateway-works#modifications-to-the-request)
  are removed, and IPv6 addresses are normalized to their `/64` network. Leave the setting at `1` (or
  your real hop count) unless you deliberately want to stop capturing client IPs.

<Warning>
  Setting `TRUSTED_PROXY_HOP_COUNT` **higher** than your real hop count lets a client spoof its IP by
  sending a forged `X-Forwarded-For` header. Set it to the exact number of proxies in front of the app —
  no higher. The default of `1` is correct for a single reverse proxy / ingress.
</Warning>

### Renamed Configuration

- **Scheduling variables renamed.** `NEXT_PUBLIC_SURVEY_SCHEDULING_*` → `SURVEY_SCHEDULING_*` (the
  `NEXT_PUBLIC_` prefix was dropped). This only affects you if you ran a v5.3 release candidate that used
  the old names; a clean v5.2 → v5.3 upgrade never set them.

### Optional New Configuration

None of the following is required to run v5.3. Add them only if you want the associated feature.

#### Survey Scheduling

The new survey-scheduling feature runs on a fixed daily local time. All three are optional and defaulted:

- `SURVEY_SCHEDULING_TIME_ZONE` — a valid IANA time zone. Default `Europe/Berlin`.
- `SURVEY_SCHEDULING_LOCAL_HOUR` — default `0`.
- `SURVEY_SCHEDULING_LOCAL_MINUTE` — default `0`.

#### Password Breach Check

- `PASSWORD_HIBP_CHECK_DISABLED` — set to `"1"` to disable the "Have I Been Pwned" breached-password
  check on sign-up and password reset (`"0"` or unset keeps it on).

## v5.2

Forma v5.2 migrates authentication from NextAuth to **Better Auth**. For most self-hosted
instances this is a drop-in upgrade, but **if you use SSO (Azure AD / Entra ID, generic OIDC, or SAML)
you must re-register the OAuth callback URL at your identity provider before the first v5.2 restart**,
or SSO sign-in will fail with a redirect-URI mismatch.

<Warning>
  All users are signed out once when you upgrade to v5.2. Better Auth takes over session handling and
  there is no dual-read from the old NextAuth sessions, so the cutover is a one-time forced re-login.
  Passwords are preserved — existing credential hashes are migrated automatically, so no password reset
  is needed.
</Warning>

### SSO Callback URL Change (action required for SSO users)

Better Auth serves the OAuth2/OIDC callback at a new path:

- old (NextAuth): `/api/auth/callback/{provider}`
- new (Better Auth): `/api/auth/oauth2/callback/{providerId}`

Update the redirect / callback URIs at your identity provider to the new path. Replace `https://your-domain.com`
with your instance URL:

| Provider | Where to update | New callback URL |
| --- | --- | --- |
| Azure AD / Entra ID | Azure portal -> App registration -> Authentication -> Redirect URIs | `https://your-domain.com/api/auth/oauth2/callback/azuread` |
| Generic OIDC | At your OIDC provider | `https://your-domain.com/api/auth/oauth2/callback/openid` |
| SAML (BoxyHQ / Jackson) | The Jackson connection's `redirect_uri` | `https://your-domain.com/api/auth/oauth2/callback/saml` |

<Note>
  **Google and GitHub sign-in do not change.** They use Better Auth's built-in social providers, whose
  callback path (`/api/auth/callback/{provider}`) is unchanged — nothing to do there.

  For SAML, only the Jackson connection's `redirect_uri` changes. The IdP-side ACS endpoint
  (`/api/auth/saml/callback`) is unchanged, so you do **not** need to reconfigure your IdP's SAML app.

  Leave the old `/api/auth/callback/*` redirect URIs registered through the transition. Keeping them in
  place is harmless and makes a rollback to v5.1 clean.
</Note>

### Authentication Environment Variables

Better Auth introduces two optional variables. **Neither is required** for a standard upgrade — both fall
back to your existing NextAuth configuration:

- `BETTER_AUTH_SECRET` — cookie/session signing secret. Falls back to `NEXTAUTH_SECRET` when unset. If you
  set it explicitly it must be at least 32 characters. Keeping the `NEXTAUTH_SECRET` fallback is
  recommended so the value the forward-auth proxy already verifies with stays consistent.
- `BETTER_AUTH_URL` — the auth base URL. Falls back to `NEXTAUTH_URL` (and then `WEBAPP_URL`) when unset.

<Info>
  If your instance already sets `NEXTAUTH_SECRET` and `NEXTAUTH_URL` (all v5.1 instances do), you can
  upgrade without adding any new auth variables.
</Info>

**Removed:** `DISABLE_ACCOUNT_DELETION_SSO_CONFIRMATION` no longer exists. Remove it from your environment
if you set it; it now has no effect.

None of the following is required to run v5.2. Add them only if you want the associated feature.

## v5

Forma v5 changes the self-hosted runtime contract. If you are upgrading an existing Forma 4.x
deployment, review this section before starting the new version.

### What Changes In v5


- **Edge rate limiting is now required** for specific public and API-key routes. Those routes are no longer
  throttled inside the application server.
- **AI features are configured at the instance level** via `AI_*` environment variables.

<Warning>
  Forma v5 removes application-level rate limiting for several routes that are now expected to be
  protected by Envoy Gateway or an equivalent edge rate limiter. If your self-hosted instance does not
  already have equivalent edge protection, add it before exposing the v5 stack.
</Warning>

### Before You Upgrade

Before you restart your instance on Forma v5:

- back up your database
- identify your current deployment type: one-click, manual Docker Compose, or Kubernetes/Helm
- confirm Redis/Valkey and your file storage setup are already healthy from your v4 baseline
- identify whether file uploads use external S3-compatible storage or a legacy bundled MinIO service
- decide whether this instance needs optional AI features
- verify whether you already run Envoy Gateway or another equivalent edge rate limiter for the covered routes

### Required Config And Infrastructure Changes

#### Edge Rate Limiting

Forma v5 splits rate limiting across two layers:

- Envoy Gateway, or an equivalent edge rate limiter, for covered public and API-key routes
- the application server for the remaining session-authenticated routes, server actions, and uncovered APIs

Keep Redis/Valkey enabled for the remaining application-enforced limits. For the covered route groups and exact
thresholds, use the [rate-limiting guide](/self-hosting/advanced/rate-limiting) as the source of truth.

#### AI Features

AI features are optional and only need instance-level configuration if you want to enable the related
enterprise functionality.

- `AI_PROVIDER` and `AI_MODEL` are the base settings
- `AI_PROVIDER=aws` requires `AI_AWS_REGION`, `AI_AWS_ACCESS_KEY_ID`, and `AI_AWS_SECRET_ACCESS_KEY`
- `AI_PROVIDER=google` requires `AI_GOOGLE_CLOUD_PROJECT` and `AI_GOOGLE_CLOUD_LOCATION`; credentials are
  optional overrides when Application Default Credentials are unavailable
- `AI_PROVIDER=azure` requires `AI_AZURE_API_KEY` and either `AI_AZURE_BASE_URL` or
  `AI_AZURE_RESOURCE_NAME`
- `AI_PROVIDER=openai-compatible` requires `AI_OPENAI_COMPATIBLE_BASE_URL`; the LLM GA v1 self-hosted
  path is Qwen served by vLLM
- Helm operators can set `llm.enabled: true` to deploy the bundled Qwen/vLLM runtime
- Docker Compose operators can set `COMPOSE_PROFILES=qwen` to deploy the bundled Qwen/vLLM runtime
- Keep the bundled runtime disabled when you configure Google Vertex, Azure, AWS Bedrock, or an external
  OpenAI-compatible endpoint manually

## v4.7

Forma v4.7 introduces **typed contact attributes** with native `number` and `date` data types. This enables comparison-based segment filters (e.g. "signup date before 2025-01-01") that were previously not possible with string-only attribute values.

### What Happens Automatically

When Forma v4.7 starts for the first time, the data migration will:

1. Analyze all existing contact attribute keys and infer their data types (`text`, `number`, or `date`) based on the stored values
2. Update the `ContactAttributeKey` table with the detected `dataType` for each key
3. **If your instance has fewer than 1,000,000 contact attribute rows**: backfill the new `valueNumber` and `valueDate` columns inline. No manual action is needed.
4. **If your instance has 1,000,000 or more contact attribute rows**: the value backfill is skipped to avoid hitting the migration timeout. You will need to run a standalone backfill script after the upgrade.

<Info>
  Most self-hosted instances have far fewer than 1,000,000 contact attribute rows (a typical setup with 100K
  contacts and 5-10 attributes each lands around 500K-1M rows). If you are below the threshold, the migration
  handles everything automatically and you can skip the manual backfill step below.
</Info>

Key characteristics of the backfill script:

- **Safe to run while Forma is live** -- it does not lock the entire table or wrap work in a long transaction
- **Idempotent** -- it only updates rows where the typed columns are still `NULL`, so you can safely run it multiple times

Forma 4.0 is a **major milestone** that sets up the technical foundation for future iterations and feature improvements. This release focuses on modernizing core infrastructure components to improve reliability, scalability, and enable advanced features going forward.

### What's New in Forma 4.0

**🚀 New Enterprise Features:**

- **Quotas Management**: Advanced quota controls for enterprise users

**🏗️ Technical Foundation Improvements:**

- **Enhanced File Storage**: Improved file handling with better performance and reliability
- **Improved Caching**: New caching functionality improving speed, extensibility and reliability

### What This Means for Your Self-Hosting Setup

These improvements in Forma 4.0 also make some infrastructure requirements mandatory going forward:

- **Redis** for caching
- **RustFS or S3-compatible storage** for file uploads

These services are already included in the updated one-click setup for self-hosters, but existing users need to upgrade their setup. More information on this below.

### Why We Made These Changes

We know this represents more moving parts in your infrastructure and might even introduce more complexity in hosting Forma, and we don't take this decision lightly. As Forma grows into a comprehensive Survey and Experience Management platform, we've reached a point where the simple, single-service approach was holding back our ability to deliver the reliable, feature-rich product our users demand and deserve.

By moving to dedicated, professional-grade services for these critical functions, we're building the foundation needed to deliver:

- **Enterprise-grade reliability** with proper redundancy and backup capabilities
- **Advanced features** that require sophisticated caching and file processing
- **Better performance** through optimized, dedicated services
- **Future scalability** to support larger deployments and more complex use cases without the need to maintain two different approaches

We believe this is the only path forward to build the comprehensive Survey and Experience Management software we're aiming for.

#### Redis

Forma 4.0 requires a Redis instance to work properly. Please add a Redis instance to your Docker setup, your K8s infrastructure, or however you are hosting Forma at the moment. Forma works with the latest versions of Redis as well as Valkey.

You need to configure the `REDIS_URL` environment variable and point it to your Redis instance.

#### S3-compatible storage

To use file storage (e.g., file upload questions, image choice questions, custom survey backgrounds, etc.), you need to have S3-compatible file storage set up and connected to Forma.

Forma supports multiple storage providers (among many other S3-compatible storages):

- AWS S3
- Digital Ocean Spaces
- Hetzner Object Storage
- Custom RustFS server

Please make sure to set up a storage bucket with one of these solutions and then link it to Forma using the following environment variables:

```
  S3_ACCESS_KEY: your-access-key
  S3_SECRET_KEY: your-secret-key
  S3_REGION: us-east-1
  S3_BUCKET_NAME: forma-uploads
  S3_ENDPOINT_URL: https://files.yourdomain.com # not needed for AWS S3
  S3_FORCE_PATH_STYLE: 1 # set this only for custom endpoints like RustFS, MinIO, or LocalStack; omit for AWS S3
```

To follow these steps, go to the folder where your `docker-compose.yml` file is located.

1. **Backup your Database**: This step is important. Please make sure to back up your database before upgrading. You can use the following command to back up your database:

```bash
docker exec forma-postgres-1 pg_dump -Fc -U postgres -d forma > forma_pre_v2.4_$(date +%Y%m%d_%H%M%S).dump
```

<Info>
  If you run into “No such container”, use `docker ps` to find your container name,
  e.g. `forma_postgres_1`.
</Info>

<Info>
  If you prefer storing the backup as a `*.sql` file, remove the `-Fc` (custom format) option. In case of a
  restore scenario, you will need to use `psql` then with an empty `forma` database.
</Info>

- Pull the latest version of Forma:

```bash
docker compose pull
```

- Stop the running Forma instance & remove the related containers:

```bash
docker compose down
```

- Restarting the containers with the latest version of Forma:

```bash
docker compose up -d
```

Now let's migrate the data to the latest schema:

To find your Docker Network name for your Postgres Database, find it using `docker network ls`

```bash
docker pull ghcr.io/yldm-tech/data-migrations:v2.4.3 && \
docker run --rm \
  --network=forma_default \
  -e DATABASE_URL="postgresql://postgres:postgres@postgres:5432/forma" \
  -e UPGRADE_TO_VERSION="v2.4" \
  ghcr.io/yldm-tech/data-migrations:v2.4.3
```

The command above will migrate your data to the latest schema. This is an important step to update your data structure. Changes are only applied if the script runs successfully. You can run the script multiple times without issues.

- That's it! Once the migration is done, you can access your Forma instance at the same URL as before.

import forma from "@forma/js";

import forma from "@forma/js/website";

import forma from "@forma/js/app";

});

- **`RENDER_EXTERNAL_URL`**: Was used as an external URL to Render (used instead of `WEBAPP_URL`), but from v1.1, you can just set the `WEBAPP_URL` environment variable.

- **`HEROKU_APP_NAME`**: Was used to build the App name on a Heroku hosted webapp, but from v1.1, you can just set the `WEBAPP_URL` environment variable.

- **`NEXT_PUBLIC_WEBAPP_URL`**: Was used for the same purpose as `WEBAPP_URL`, but from v1.1, you can just set the `WEBAPP_URL` environment variable.

- **`PRISMA_GENERATE_DATAPROXY`**: Was used to tell Prisma that it should generate the runtime for Dataproxy usage. But its officially deprecated now.

### Helper Shell Script

For a seamless migration, below is a shell script for your self-hosted instance that will automatically update your environment variables to be compliant with the new naming conventions.

### Docker & Single Script Setup

Now that these variables can be defined at runtime, you can append them inside your `x-environment` in the `docker-compose.yml` itself.
For a more detailed guide on these environment variables, please refer to the
[Environment Variables](/self-hosting/configuration/environment-variables) page.

```yaml docker-compose.yml
version: "3.3"
x-environment: &environment
  environment:
    # The url of your Forma instance used in the admin panel
    WEBAPP_URL:

    # Required for next-auth. Should be the same as WEBAPP_URL
    NEXTAUTH_URL:

    # PostgreSQL DB for Forma to connect to
    DATABASE_URL: "postgresql://postgres:postgres@postgres:5432/forma"

    # NextJS Auth
    # @see: https://next-auth.js.org/configuration/options#nextauth_secret
    # You can use: `openssl rand -hex 32` to generate one
    NEXTAUTH_SECRET:

    # PostgreSQL password
    POSTGRES_PASSWORD: postgres

    # Email Configuration
    MAIL_FROM:
    MAIL_FROM_NAME:
    SMTP_HOST:
    SMTP_PORT:
    SMTP_SECURE_ENABLED:
    SMTP_USER:
    SMTP_PASSWORD:

    # Uncomment the below and set it to 1 to disable Email Verification for new signups
    # EMAIL_VERIFICATION_DISABLED:

    # Uncomment the below and set it to 1 to disable Password Reset
    # PASSWORD_RESET_DISABLED:

    # Uncomment the below and set it to 1 to disable Signups
    # SIGNUP_DISABLED:

    # Uncomment the below and set it to 1 to disable loging in with email
    # EMAIL_AUTH_DISABLED:

    # Uncomment the below and set it to 1 to disable Invites
    # INVITE_DISABLED:

    # Uncomment the below and set a value to have your own Privacy Page URL on the signup & login page
    # PRIVACY_URL:

    # Uncomment the below and set a value to have your own Terms Page URL on the auth and the surveys page
    # TERMS_URL:

    # Uncomment the below and set a value to have your own Imprint Page URL on the auth and the surveys page
    # IMPRINT_URL:

    # Uncomment the below and set to 1 if you want to enable GitHub OAuth
    # GITHUB_AUTH_ENABLED:
    # GITHUB_ID:
    # GITHUB_SECRET:

    # Uncomment the below and set to 1 if you want to enable Google OAuth
    # GOOGLE_AUTH_ENABLED:
    # GOOGLE_CLIENT_ID:
    # GOOGLE_CLIENT_SECRET:
```
